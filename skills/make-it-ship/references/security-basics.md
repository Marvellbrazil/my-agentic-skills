# Security basics

Source group 1. Assess every project; mark individual controls N/A only when the corresponding capability is absent. PASS requires evidence for the named environment, not merely a dependency or configuration name. Use the status and reporting contract in [SKILL.md](../SKILL.md).

| ID | Source item | Applicability, interpretation and evidence to seek |
| ----- | ------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| SB-01 | Hide API keys | Private credentials: inspect client bundles, tracked configuration and logs with redaction. Server environment variables or a secret manager must not flow into public output. Intentionally publishable keys belong to SB-03. Related: PF-14, AH-06. |
| SB-02 | Purge Git secrets | Inspect authorized repository history using redacted secret-scanner results and named revision coverage. A clean working tree does not prove clean history. On exposure, propose revoke/rotate and incident review first, then separately authorized, coordinated history cleanup; never rewrite or force-push during this audit. Related: AH-02. |
| SB-03 | Use public DB key | Only for providers designed for client access. Verify the key is explicitly publishable/anon, not a database password or secret/service-role key. Inspect least-privilege grants and policies; a public key is neither user authentication nor authorization. Server-only database credentials remain private. |
| SB-04 | Enable row-level security | For exposed database tables or an architecture requiring RLS: inspect policies for each operation, tenant/user boundary, grants, owner/bypass roles and cross-user test evidence. Enabling RLS alone is insufficient. Do not mandate a specific RLS feature where equivalent server-enforced authorization is the intended architecture. Related: SA-20. |
| SB-05 | Encrypt sensitive data | Identify data sensitivity, transit, storage, backups, device protection and key custody. Seek actual encryption/protection settings and access boundaries. Hash passwords under SB-10; do not require reversible password encryption. Platform encryption may satisfy the requirement; app-layer encryption depends on the threat model. |
| SB-06 | Enforce server-side auth | Protected service operations: inspect session/token validation, expiry, issuer/audience where applicable, and rejection evidence. Client-side route guards alone fail. Offline apps may require local protection, not an invented auth server. Related: AH-07, AH-15. |
| SB-07 | Lock record access | Data access: inspect ownership/tenant filtering for every read and mutation, including exports, downloads and bulk routes. Seek two-user/two-tenant negative tests; a valid login is not record authorization. Related: AH-04. |
| SB-08 | Block field tampering | Mutations: verify explicit writable-field allowlists and server-owned role, price, owner and status fields. Inspect malicious-field tests; schema type validation alone does not grant permission to edit a field. Related: SA-08. |
| SB-09 | Secure session cookies | Cookie sessions: inspect actual Set-Cookie behavior, scope, lifetime, rotation and invalidation. Require Secure, HttpOnly for session secrets, and an appropriate SameSite policy; cross-site flows need deliberate CSRF protection. Related: SA-19; session revocation is separately SA-03. |
| SB-10 | Hash passwords | Password-based auth: inspect provider configuration or a maintained adaptive password-hashing implementation, salted hashes and appropriate current cost settings. Fast general-purpose hashes and plaintext fail. Do not build custom crypto or demand password storage from an external identity-provider client. Related: AH-05. |
| SB-11 | Rate limit login | Login endpoints: seek server-side per-account and network-aware throttling, bounded distributed enforcement and negative tests. IP-only rules can punish shared networks; consider credential stuffing and lockout abuse. Related: SA-17, AH-03. |
| SB-12 | Add bot protection | Public abuse-prone flows: assess threat and existing throttling first. When challenges are used, verify server-side token validation, expiry/replay handling and accessible alternatives. CAPTCHA is not mandatory for every product and does not replace auth or rate limits. |
| SB-13 | Parameterize queries | Database queries: inspect all raw query paths for bound parameters; allowlist dynamic identifiers separately. ORM usage is not evidence that every raw expression is safe. Seek injection-focused unit/integration evidence without attacking production. |
| SB-14 | Validate all input | Untrusted boundaries: inspect type, length, range, nesting, business rules and size limits, including APIs, imports and webhooks. Client validation improves UX but does not replace server validation. Related: SA-11, SA-13, AH-09. |
| SB-15 | Escape user content | Rendering paths: verify output encoding for HTML, attributes, URLs, script and other contexts; inspect unsafe rendering sinks. Use maintained HTML sanitization when rich markup is intentionally supported. Do not pre-escape all stored strings or treat validation as XSS protection. Related: AH-10. |
| SB-16 | Restrict file uploads | Upload/import surfaces: verify authorized upload/download, type and size limits, generated safe names, storage outside executable paths, and bounded processing/decompression. Client MIME or extensions alone are insufficient. Related: SA-06, SA-11. |
| SB-17 | Trim API responses | APIs: inspect explicit response fields and authorization; ensure hashes, credentials, internal errors and other users' data are absent. Verify sensitive responses are not shared-cached. Payload compression is separate from data minimization. |
| SB-18 | Add security headers | Web responses: inspect appropriate CSP, anti-framing policy, nosniff and referrer controls plus deployed response evidence. Header needs vary by HTML/API/embed surface. Do not recommend obsolete X-XSS-Protection as a substitute for CSP/encoding. Related: AH-17, SA-01. |
| SB-19 | Force HTTPS | Networked production: seek TLS/certificate and HTTP redirect evidence, secure upstream/proxy handling and absence of mixed content. A local HTTPS setting is not proof of deployment. HSTS is separately SA-01. |
| SB-20 | Scan dependencies | Dependencies: review lockfiles and dated advisory scan results, affected versions, reachability and remediation. Record scanner scope and failures. A clean scan is not proof of overall security; updates need compatibility checks and are recommendations only. Related: AH-08. |

## Supporting guidance

Consult current official provider documentation for concrete configurations; do not copy parameters blindly across versions.

- [Supabase client keys and data access](https://github.com/supabase/supabase/blob/master/apps/docs/content/guides/database/secure-data.mdx), checked through Context7 on 2026-10-12: publishable/anon keys require grants and access policies; secret/service-role credentials bypass RLS and stay server-side.
- [OWASP authentication guidance](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html).
- [OWASP XSS prevention](https://cheatsheetseries.owasp.org/cheatsheets/Cross_Site_Scripting_Prevention_Cheat_Sheet.html).
- [OWASP file uploads](https://cheatsheetseries.owasp.org/cheatsheets/File_Upload_Cheat_Sheet.html).

These sources were consulted on 2026-10-12; refresh version-dependent recommendations during an actual audit.
